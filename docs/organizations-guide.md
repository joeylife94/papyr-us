# 조직(Organization) 가이드

이 문서는 #124 X1a에서 들어온 조직 경계, X1b에서 나머지 공유 영역에 적용한 범위, X1c에서 들어온 조직 관리(생성, 구성원과 역할, 설정, 조직별 AI)를 설명합니다. 코드 기준은 `shared/schema.ts`(`organizations`, `organization_members`), `server/storage.ts`(`readableBy`, `listableBy`, `checkPagePermission`, `getUserTeamIds`, `withOrganizationLocks`), `server/organization-routes.ts`, `server/organization-admin-routes.ts`, `server/organization-guards.ts`, `drizzle/0022_add_organizations.sql` ~ `0024_add_organization_ai_setting.sql`입니다.

## 조직이란

- 조직은 테넌트 경계입니다. 모든 팀과 모든 페이지는 정확히 한 조직에 속합니다.
- 계정은 지금은 **최대 한 조직**에 속합니다(`organization_members_user_id_unique`). 그래서 요청이 어느 조직의 것인지는 로그인한 계정만 보고 정해지며, URL이나 화면에 조직을 고르는 단계가 없습니다.
- 조직 역할은 `owner` / `admin` / `member`입니다. 가입한 계정은 `member`로 시작하고, 역할은 아래 [조직 관리](#조직-관리-x1c)의 규칙으로만 바뀝니다.
- 플랫폼 관리자([rbac-guide.md](./rbac-guide.md))는 조직 위에 있는 운영자 권한입니다. 조직을 만들고 첫 소유자를 지정할 수 있지만, 그것만으로 어떤 조직의 페이지도 볼 수 없고 소유자가 있는 조직의 구성원이나 설정을 바꿀 수도 없습니다.

## 경계 규칙

다른 조직으로 넘어가는 것은 **명시적으로 공개 공유한 페이지(public 권한)뿐**입니다.

- **단일 페이지:** public 권한이 아니면, 페이지 조직의 로그인한 구성원만 접근할 수 있습니다. 작성자, 사용자 권한, 팀 권한, 팀 멤버십 어느 것도 다른 조직 계정에게는 효력이 없습니다.
- **권한 행이 없는 팀 없는 페이지(예전 "열린" 페이지):** 같은 조직의 로그인한 구성원에게만 열립니다. 비로그인 사용자와 다른 조직 계정에게는 열리지 않습니다. (X1a 이전에는 누구에게나 열려 있었습니다.)
- **목록:** 검색, 페이지 트리, 링크 선택기, 폴더, 백링크, 태그, 휴지통, 지식 그래프, AI 검색은 자기 조직의 페이지만 보여 줍니다. 다른 조직의 공개 페이지도 목록에는 나오지 않고 링크로만 열립니다. 비로그인 상태에서는 아무것도 나열되지 않습니다.
- **팀:** 팀 멤버십과 팀 역할은 계정 자신의 조직 안 팀에서만 인정됩니다(`getUserTeamIds`, `getUserTeamRole`). 그래서 팀 단위로 묶인 모든 라우트(캘린더, 태스크, 멤버 등)도 조직 밖으로 나가지 않습니다.
- **쓰기:**
  - 새 팀은 만든 사람의 조직에 속하며, 로그인하지 않으면 팀을 만들 수 없습니다.
  - 새 페이지는 팀의 조직, 팀이 없으면 만든 사람의 조직에 속합니다. 둘 다 없으면 만들지 않습니다(`OrganizationRequiredError`).
  - 팀 페이지의 조직은 언제나 그 팀의 조직입니다. 이건 DB 제약 `wiki_pages_team_org_fk`가 보장합니다.
  - 팀 멤버 추가(`POST /api/teams/:teamId/memberships`)와 페이지 권한 부여(`POST /api/pages/:id/permissions`)는 같은 조직의 계정과 팀만 받습니다. 다른 조직 대상은 없는 계정·팀과 같은 응답을 받습니다.
- **조직 id는 클라이언트가 정하지 않습니다:** API의 페이지·팀 입력 스키마에서 `organizationId`는 빠져 있습니다.

## 나머지 공유 영역 (X1b)

X1b는 페이지와 팀 밖의 공유 영역에 같은 경계를 적용했습니다. 공통 규칙은 두 가지입니다.

- **쓰기는 항상 로그인이 필요합니다.** 아래 영역의 생성·수정·삭제는 `ENFORCE_AUTH_WRITES`가 꺼져 있어도 세션이 없으면 401입니다.
- **볼 수 없는 대상은 없는 대상과 똑같이 답합니다.** 다른 조직이나 다른 팀의 것인지, 원래 없는 것인지 응답으로 구분할 수 없습니다.

| 영역                                                                     | 규칙                                                                                                                                                                                                                                                                                |
| ------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 통계 (`/api/stats/dashboard`, `/api/stats/overview`)                     | 항상 로그인 필요. 호출자가 목록에서 볼 수 있는 페이지, 그 페이지의 댓글, 자기 팀의 태스크, 자기 조직의 계정만 셉니다.                                                                                                                                                               |
| 페이지 분석 (`POST /api/pages/:id/view`, `GET /api/pages/:id/analytics`) | 페이지 읽기 규칙을 따릅니다. 읽을 수 없는 페이지의 조회는 기록되지 않습니다.                                                                                                                                                                                                        |
| 인기 페이지 (`GET /api/analytics/popular`)                               | 호출자가 목록에서 볼 수 있는 살아 있는 페이지만 순위에 오릅니다(#141).                                                                                                                                                                                                              |
| 즐겨찾기                                                                 | 목록에서 볼 수 있는 살아 있는 페이지만 추가되고 나열됩니다. 그 밖의 페이지는 404입니다. 가려진 행은 지워지지 않습니다.                                                                                                                                                              |
| 활동 피드 (`GET /api/activity`)                                          | 자기 팀의 행, 그리고 팀이 없는 행 중 대상이 볼 수 있는 페이지인 것만 보입니다.                                                                                                                                                                                                      |
| 알림                                                                     | 알림의 수신자는 `members` 행이고, 계정은 이메일이 같은 `members` 행의 알림만 읽고 고칩니다. 남의 알림은 404입니다. 새 알림은 같은 조직의 수신자, 자신의 발신자 행, 자신이 읽을 수 있는 페이지·댓글·자기 팀의 태스크만 가리킬 수 있습니다. 실시간 이벤트는 수신자 계정에게만 갑니다. |
| 워크플로                                                                 | 팀이 있어야 만들 수 있습니다. 팀 없는 페이지의 이벤트는 어떤 워크플로도 실행하지 않습니다. 액션은 워크플로 팀의 페이지·태스크에만 작용하고, 만든 페이지·태스크는 그 팀에 들어가며, 알림은 팀 조직의 구성원에게만 갑니다. 테스트 실행도 같은 제한을 받습니다.                        |
| 저장된 뷰                                                                | 팀이 있어야 만들 수 있습니다.                                                                                                                                                                                                                                                       |
| 템플릿                                                                   | 조직의 데이터입니다(`templates.organization_id`, `drizzle/0023_add_template_organizations.sql`). 항상 로그인이 필요하고 자기 조직의 템플릿만 읽고 고칩니다. 카테고리는 인스턴스 공용이며 플랫폼 관리자만 바꿉니다.                                                                  |
| 업로드                                                                   | 올리기, 목록, 읽기, 삭제 모두 로그인이 필요합니다. 파일 옆 메타데이터에 조직과 올린 계정을 기록합니다. 팀 파일은 그 팀 구성원만, 팀 없는 파일은 같은 조직의 계정만 읽고 지웁니다. 파일명은 업로드가 만든 이름 하나만 받습니다.                                                      |

X1b 이전에 만들어진 데이터는 지우지 않고 다음처럼 다룹니다.

- **팀 없는 워크플로와 저장된 뷰:** 행은 남지만 누구에게도 보이지 않습니다(404). 다시 쓰려면 팀을 지정해 새로 만들어야 합니다.
- **조직 정보가 없는 업로드 메타데이터:** `default` 조직의 파일로 봅니다. 팀 이름으로 기록된 예전 파일도 `default` 조직의 팀일 때만 그 팀의 것으로 인정합니다.
- **메타데이터가 없는 업로드 파일:** API로 읽거나 지울 수 없습니다(403). 정리는 서버에서 직접 해야 합니다.
- **읽을 수 없는 페이지에 남아 있던 조회 기록과 즐겨찾기:** 행은 남지만 순위와 목록에 나오지 않습니다.

## 조직 관리 (X1c)

### 플랫폼 관리자: 조직 만들기와 첫 소유자

관리자 패널(`/admin`)의 `Organizations` 탭, API는 `/api/admin/organizations*`입니다. 플랫폼 관리자가 아니면 403입니다.

- **조직 목록**은 이름, slug, 구성원 수, 소유자 수, AI 설정만 보여 줍니다. 구성원의 이름이나 이메일은 나오지 않습니다.
- **조직 만들기**는 이름, slug, 첫 소유자의 이메일을 받습니다. 새 조직은 **AI가 꺼진 상태**로 시작합니다.
- **첫 소유자가 될 수 있는 계정은 다른 조직에 아무것도 남기지 않은 계정뿐입니다.** 다음 중 하나라도 있으면 거부하고(409 `account_not_eligible`), 무엇 때문인지 `reasons`로 알려 줍니다. 아무것도 자동으로 옮기거나 지우지 않습니다.

  | `reasons` 값       | 뜻                                         |
  | ------------------ | ------------------------------------------ |
  | `holds_role`       | 다른 조직에서 `member`보다 높은 역할       |
  | `team_memberships` | 다른 조직의 팀에 속해 있음                 |
  | `authored_pages`   | 다른 조직에 직접 쓴 페이지가 있음          |
  | `page_grants`      | 다른 조직의 페이지에 받은 권한이 있음      |
  | `comments`         | 다른 조직의 페이지에 쓴 댓글이 있음        |
  | `roster_rows`      | 다른 조직 팀의 명단(`members`)에 올라 있음 |

  이 조건은 계정을 옮기는 순간에 원래 조직의 잠금 아래에서 검사합니다. DB 제약은 아니어서, 바로 그 순간에 진행 중이던 그 계정의 쓰기 하나가 원래 조직에 남을 수는 있습니다. 그렇게 남은 행으로는 원래 조직의 어떤 것도 읽거나 고칠 수 없습니다.

- **소유자가 없는 조직에 한해**, 플랫폼 관리자가 그 조직의 기존 구성원 한 명을 소유자로 올릴 수 있습니다(`POST /api/admin/organizations/:id/owners`). `default` 조직의 첫 소유자는 이렇게 정합니다. 소유자가 한 명이라도 있으면(비활성 계정 포함) 409 `organization_has_owner`이며, 그 뒤로는 조직 안의 소유자만 역할을 바꿉니다.
- 다른 조직에서 계정을 데려오는 방법은 첫 소유자 지정뿐입니다. 구성원을 추가하는 초대는 X1d에서 들어옵니다.

### 소유자와 관리자: 구성원, 팀, 설정

화면은 `/organization`(사용자 메뉴의 `조직 관리`), API는 `/api/organization*`입니다. 어느 조직인지는 로그인한 계정으로만 정해지고, 요청으로 조직을 지정할 수 없습니다.

| 호출자           | `GET /api/organization` | 구성원·팀 목록, 설정 변경, 역할 변경, 내보내기 |
| ---------------- | ----------------------- | ---------------------------------------------- |
| 비로그인         | 401                     | 401                                            |
| 조직이 없는 계정 | 403                     | 403                                            |
| `member`         | 자기 조직과 자기 역할   | 403                                            |
| `admin`, `owner` | 자기 조직과 자기 역할   | 아래 규칙대로                                  |

역할 변경(`PATCH /api/organization/members/:userId`)과 내보내기(`DELETE /api/organization/members/:userId`)의 규칙:

- **`owner` 역할을 주거나 바꾸는 것은 `owner`만** 할 수 있습니다. `admin`은 `owner`나 다른 `admin`을 바꾸거나 내보낼 수 없고, `member`를 `admin`으로 올리거나 `admin`인 자신을 `member`로 내릴 수는 있습니다.
- 자신의 역할을 스스로 올릴 수 없고, 자신을 내보낼 수 없습니다.
- **마지막 활성 소유자는 내려가거나 나갈 수 없습니다**(409). 비활성 계정은 소유자 수에 세지 않습니다.
- 다른 조직의 계정은 없는 계정과 같은 404를 받습니다.
- 판단은 조직 단위 잠금 안에서, 잠금을 얻은 뒤 다시 읽은 값으로 합니다. 그래서 두 소유자가 동시에 서로를 내려도 소유자가 0명이 되지 않습니다. 잠금을 5초 넘게 기다리면 503이고, 다시 시도하면 됩니다.

구성원을 내보내면:

- 조직 멤버십, 그 조직 팀들의 팀 멤버십, 그 조직 페이지에 받은 사용자 권한이 한 트랜잭션에서 지워집니다. 열려 있던 실시간 편집 세션도 그 자리에서 권한을 다시 확인합니다.
- **계정, 그 계정이 쓴 페이지와 댓글, 팀 명단(`members`) 행은 지우지 않습니다.** 계정은 로그인은 되지만 조직이 없어서, 조직의 페이지·팀·알림 어느 것도 읽거나 고칠 수 없습니다. 자기 댓글도 그 페이지에 댓글을 달 권한이 있는 동안에만 고치거나 지울 수 있습니다.
- 유일한 팀 소유자였다면 그 팀은 소유자 없이 남고, 응답의 `teamsLeftWithoutOwner`에 나옵니다. 그 팀의 페이지와 남은 구성원은 그대로이지만, 소유자를 다시 지정하는 기능은 아직 없습니다(아래 범위 밖 항목).

설정(`PATCH /api/organization`)은 조직 이름과 AI 사용 여부 두 가지이고, `owner`와 `admin`이 바꿉니다.

### 조직별 AI

- 조직마다 AI 사용 여부가 있습니다(`organizations.ai_enabled`). **`default` 조직은 켜져 있고, 관리자 API로 만든 새 조직은 꺼져 있습니다.**
- 꺼져 있는 조직의 내용은 AI 제공자에게 가지 않습니다. 서버의 모든 AI 경로가 호출자의 조직을 확인합니다.
  - `/api/ai/*`는 로그인이 필요하고(`ENFORCE_AUTH_WRITES`와 무관하게 비로그인은 401), 조직이 없거나 AI가 꺼져 있으면 403(`code: "ai_disabled"`)입니다.
  - AI 검색(`POST /api/ai/search`)은 거부하지 않고 AI 재정렬 없이 전문 검색 결과를 돌려줍니다.
  - 지식 그래프의 AI 링크 제안(`includeAI=true`)은 403이고, 제안 없는 그래프는 그대로 나옵니다.
  - 워크플로의 AI 요약 액션은 **워크플로가 속한 팀의 조직**을 따르며, 꺼져 있으면 그 액션만 실패로 기록됩니다.
- **페이지의 AI는 페이지가 속한 조직도 따릅니다.** 공개 공유로 다른 조직의 페이지를 열었을 때는 AI 기능이 보이지 않고 요청도 보내지 않습니다.
- 조직의 설정을 확인할 수 없으면(조회 실패 등) 꺼진 것으로 다룹니다.
- 화면은 꺼져 있는 조직에서 AI 진입점(코파일럿, 관련 페이지, 인라인 AI, 검색 제안, 그래프의 AI 링크, 워크플로의 AI 요약 액션)을 감추거나 비활성으로 보여 줍니다.
- 인스턴스에 AI 제공자 키가 없으면 조직 설정과 무관하게 AI는 동작하지 않습니다.

### X1c에서 함께 바뀐 것

- 플랫폼 관리자라는 이유만으로는 남의 댓글을 고치거나 지울 수 없습니다. 댓글은 작성자(그 페이지에 댓글을 달 수 있는 동안)와 그 페이지의 편집자만 다룹니다. 볼 수 없는 페이지의 댓글은 없는 댓글과 같은 404입니다.
- 조직이 없는 계정은 알림을 읽거나 고칠 수 없습니다(403).
- `PUT /api/teams/:id`는 정해진 팀 필드만 받고, `PUT`과 `DELETE` 모두 `ENFORCE_AUTH_WRITES`와 무관하게 로그인이 필요합니다.

## 가입

X1d(가입 정책) 전까지는 새 계정(이메일 가입, Google, GitHub, `db:seed`, Firebat 관리자 시드)이 모두 `default` 조직에 `member`로 들어갑니다. `default` 조직은 AI가 켜진 상태로 만들어집니다. 계정과 조직 멤버십은 한 트랜잭션에서 만들어집니다(`server/organizations.ts`). 그래서 조직이 하나뿐인 배포는 X1a 이전과 같은 공간에서 동작합니다.

## 배포와 마이그레이션

운영 배포는 SQL 마이그레이션이 아니라 `drizzle-kit push`로 스키마를 맞춥니다. push는 행이 있는 테이블에 NOT NULL 컬럼을 추가할 수 없으므로, push 전에 조직 마이그레이션을 먼저 적용해야 합니다.

```bash
npm run db:fts:prepare
npm run db:orgs:prepare   # drizzle/0022 (조직), 0023 (템플릿), 0024 (조직별 AI 설정)
npm run db:push
npm run db:fts
```

- Firebat(`Dockerfile.firebat`의 migrate 단계)과 `.github/workflows/deploy.yml`에는 이 순서가 이미 들어 있습니다.
- `db:orgs:prepare`가 하는 일:
  - 기존 계정, 팀, 페이지를 모두 `default` 조직으로 옮깁니다(0022).
  - 기존 템플릿을 모두 `default` 조직으로 옮깁니다(0023).
  - 조직별 AI 설정 컬럼을 추가합니다(0024). **그 시점에 이미 있던 조직은 모두 AI가 켜진 상태로 남습니다.** 이후 소유자나 관리자가 끈 설정은 다시 실행해도 유지됩니다.
  - 세 파일은 한 트랜잭션으로 적용됩니다.
  - 새 컬럼과 제약을 shared/schema.ts와 같은 이름으로 만듭니다. 그래서 뒤이은 push는 바꿀 것이 없습니다.
  - 여러 번 실행해도 결과가 같습니다.
- 기본 테이블이 아직 없는 새 설치에서는 아무것도 하지 않습니다. 이 경우 push가 스키마를 만들고, 첫 가입 때 `default` 조직이 만들어집니다.
- `db:orgs:prepare`를 빼먹고 기존 DB에 push하면, NOT NULL 컬럼 추가가 실패하면서 push가 멈춥니다. 이때 데이터는 바뀌지 않습니다.
- 수동 배포(`docs/ubuntu-deployment-guide.md`)도 같은 순서를 따릅니다.

### 되돌리기

```bash
node scripts/apply-organizations-schema.mjs --down   # 로컬 DB. 원격은 --allow-remote
```

- 0024, 0023, 0022의 `.down.sql`을 역순으로 적용합니다. 조직 테이블과 조직 컬럼만 지우며, 팀, 페이지, 계정, 템플릿은 남습니다.
- **조직이 둘 이상이면 실행을 거부합니다.** 조직 컬럼을 지우면 서로 다른 테넌트가 하나로 합쳐지기 때문입니다.
- **AI를 끈 조직이 하나라도 있으면 실행을 거부합니다.** 이전 버전 앱에는 조직별 스위치가 없어서, 되돌리면 그 조직의 내용이 다시 AI 제공자에게 갈 수 있기 때문입니다.
- 거부되면 아무것도 바뀌지 않습니다.
- 되돌린 뒤 이전 버전 앱을 배포해야 합니다. 새 버전 앱은 조직 컬럼이 있어야 동작합니다.

## 아직 없는 것 (#124 X1 후속)

| 단계 | 내용                                                                                                                           |
| ---- | ------------------------------------------------------------------------------------------------------------------------------ |
| X1d  | 가입 정책: 초대 링크(조직에 구성원을 추가하는 유일한 방법이 됩니다), `SIGNUP_MODE`. 검증된 도메인 가입은 X3(OIDC)로 넘어갑니다 |
| X5   | 계정 비활성화와 세션 관리. 유일한 소유자가 비활성 계정인 조직을 복구하는 절차도 여기서 정합니다                                |

X1c에서 범위 밖으로 남긴 것:

- 소유자 없이 남은 팀에 소유자를 다시 지정하는 방법이 없습니다. 조직 소유자·관리자에게도, 플랫폼 관리자에게도 그 기능이 아직 없습니다.
- 내보낸 계정의 팀 명단(`members`) 행은 남습니다. 조직이 없는 동안에는 아무 효력이 없지만, X1d에서 같은 조직에 다시 들어오면 예전 명단이 다시 인정될 수 있어 초대 설계에서 다뤄야 합니다.
- 페이지의 `author` 값은 요청 본문에서 오고, 팀 없는 명단 행은 임의의 이메일로 만들 수 있습니다. 둘 다 남의 계정을 첫 소유자 부적격으로 만들 수 있습니다.
- 관련 페이지 추천 외의 AI 라우트는 클라이언트가 보낸 본문을 그대로 제공자에게 보냅니다. 서버는 호출자의 조직만 확인하므로, 사용자가 볼 수 있는 내용을 직접 붙여 넣어 보내는 것까지 막지는 않습니다.

X1b에서 범위 밖으로 남긴 것:

- 워크플로의 페이지 액션은 댓글·태스크 이벤트의 대상 id를 페이지 id로 다룹니다(팀 밖으로 나가지는 않지만 동작이 맞지 않습니다).
- 워크플로와 저장된 뷰의 `createdBy`는 아직 클라이언트가 보낸 값을 씁니다.
- 워크플로 웹훅 URL 허용 목록, 테스트 실행의 실제 dry-run.
- 자동화 화면(`client/src/pages/automation.tsx`)은 팀 경로 밖에서 팀 없이 워크플로를 만들려 하고, 서버는 400으로 거부합니다.
- 한 조직 안에서는 구성원 누구나 그 조직의 템플릿을 고치고 지울 수 있습니다.
- 즐겨찾기에는 같은 계정·페이지의 중복을 막는 DB 제약이 없습니다.
- 팀이 없는 `members` 행은 `/api/members/:id`, `/api/members/email/:email`로 누구나 읽을 수 있습니다.
- 업로드 응답과 목록에 서버의 절대 파일 경로가 들어 있습니다.

다음 값들은 아직 인스턴스 전체에서 유일합니다. 조직마다 같은 값을 쓰려면 별도 작업이 필요합니다.

- 팀 이름(`teams.name`);
- 페이지 slug(`wiki_pages.slug`);
- 공유 링크 토큰.
